# 既存教材・アプリを安全に改修する

## 変更前

教材、実DB、ブラウザ保存、バックアップ形式、採点実装、起動手順を確認する。作業用コピーを作り、変更前の起動と代表回答を記録する。既存の採点バグがあるなら、その履歴をどう表示するかを修正内容と分けて設計する。

既存形式から共通スキーマへ変換する場合、元IDと安定した対応表を残す。IDを配列番号から振り直さない。古い版を消さず、学習者IDを表示名から再生成しない。

## 計画チェッカー

```sh
python scripts/check_migration.py old-course.json new-course.json --progress progress.json --output migration-plan.json
python scripts/check_migration.py old-course.json new-course.json --progress progress.json --id-map id-map.json --output migration-plan.json
```

`id-map.json`は例えば`{"legacy-q1":"q1"}`、または`[{"from":"legacy-q1","to":"q1"}]`。一対一の改名だけに使う。無関係な問題への付け替えに使わない。全IDを変えることが移行ではない。

終了コードは0＝計画可能、1＝停止理由あり、2＝入力／実行エラー。標準出力や`--output`に機械可読な計画が出る。元データや進捗は変更しない。`--output`に入力ファイルを指定してはいけない。

チェッカーは元・新教材の安定ID、章の参照、revision、教材version、進捗の問題と学習者参照、履歴ID、ID対応の一意性を検査する。履歴のある問題を削除する場合や、多対一のID変更は止める。問題のid／revision以外の変更も保守的にrevision増加を要求する。誤字修正や検証状態の変更でも、初版のルールに従いrevisionを上げる。

このチェッカーは任意の旧DBを自動変換するツールではない。旧アプリ固有の抽出・変換アダプターを作り、まず共通形式として検査する。正答の意味的同一性やSQLの安全性は別途確認する。

## 実際の移行

1. 教材の全問検証と旧進捗の検証を行う。
2. dry-run計画の停止理由を解消する。履歴付きの削除問題はアーカイブとして保持するか、互換参照層を具体的に作る。
3. 問題の旧revisionを履歴用に保持する。正解が変わっても過去のcorrectを現在の採点で上書きしない。
4. 実装対象に応じて移行コードを書く。DBトランザクション、一意制約、バックアップ、二重実行対策を使う。
5. コピーへ適用し、学習者数・履歴ID集合・問題参照・ブックマークを前後比較する。
6. 二度実行しても増殖・消失しないことを確認する。途中失敗を模擬し、元に戻ることを確認する。
7. 旧履歴、現行問題、解き直し、復習一覧、バックアップ復元をアプリから操作する。
8. ロールバックの手順と必要ファイルを残して、本番の許可済み範囲に適用する。

## 受け入れ条件

- 意図しないID変更・履歴消失・履歴再採点が0件。
- 削除・分割・統合が必要なら、単純なID map以外の専用移行仕様と個別検証がある。
- 旧版の回答は旧版の文脈で閲覧できる。
- 新版の問題に答えると新revisionの履歴が追加される。
- 保存形式の変更で他の学習者のデータを取り込まない。
- 同期済みの端末が古い教材を使っている場合の互換性・再取得の表示が明確。
